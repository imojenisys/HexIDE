# On macOS, a Window path naming a running form's menu by its code name finds nothing, and the reply doesn't say where the menu is — **CLOSED** (#5102, 2026-11-20)

**Symptom.** With #5065, a form's menus on macOS go in the system menu bar, and its in-window bar is hidden. A
`Window/` path naming a menu by its code name then reaches nothing, and the reply reads as if the menu didn't exist.
Measured headless on 2026-11-20 by hexide-gen, with `FormNativeMenu.UseSystemMenuBar` on, as it is on macOS, and a form
whose `mnuGame` is captioned `&Game` (`RunningFormNamesTests`):

| Exact call | Reply |
|---|---|
| `UiAutomationDriver.Resolve(window, "Window/#mnuGame")` | control `null`, error `no child matching '#mnuGame' under 'Window'` |

The tool-level rows were also measured headless on main `49f735cfd` by hexide-mcp on 2026-11-20
([#5102](https://github.com/hexide-io/HexIDE/issues/5102)), with Form1 holding Text1, Game › New and
Beginner (mnuLevel(0), plus mnuLevel(1) loaded in Form_Load), and Help › About:

| Exact call | Reply on main |
|---|---|
| `inspect_element(target: "Window/#mnuGame", window: "Form1")` | `no child matching '#mnuGame' under 'Window'` |
| `inspect_element(target: "Window/#mnuGame", window: "auto")` | `no child matching '#mnuGame' under 'Window'. The path was looked for in 'Form1', the window "auto" picked over the IDE's own` |
| `inspect_element(target: "Window/#mnuNew", window: "Form1")` | `no child matching '#mnuNew' under 'Window'` |
| `inspect_element(target: "Window/#mnuLevel(1)", window: "Form1")` | `no child matching '#mnuLevel(1)' under 'Window'` |
| `inspect_element(target: "Window/MenuItem[Game]", window: "Form1")` | `no child matching 'MenuItem[Game]' under 'Window'` |
| `inspect_element(target: "Window/#nope", window: "Form1")` | `no child matching '#nope' under 'Window'` |
| `inspect_element(target: "Window/#Text1", window: "Form1")` | resolves |
| `inspect_element(target: "Window/Menu", window: "Form1")` | resolves to the hidden in-window bar |
| `interact(target: "Window/#mnuGame", action: "expand", window: "Form1")` | `Success` false |
| `dump_visual_tree(window: "menubar", interactiveOnly: false)` | `MenuBar/MenuItem[Game]`, `MenuBar/MenuItem[Game]/MenuItem[New]`, `MenuBar/MenuItem[Game]/MenuItem[#1]`, `MenuBar/MenuItem[Game]/MenuItem[#2]` (both Beginner), `MenuBar/MenuItem[Help]`, `MenuBar/MenuItem[Help]/MenuItem[About]`; every automationId null |
| `inspect_element(target: "MenuBar/#mnuNew", window: "menubar")` | `No menu item '#mnuNew' under ''. Discover paths with dump_visual_tree(window: "menubar").` |
| `inspect_element(target: "MenuBar/MenuItem[Game]/MenuItem[#2]", window: "menubar")` | resolves, named Beginner |

The tools' Window paths reach that call through `HexIdeTools.ResolveIn`, which can add the window's name to a failure.
The tool-level reply, such as `inspect_element(target: "Window/#mnuGame", window: "Form1")`, wasn't checked on a Mac.

**Workaround.** Reach the menu by its caption through the system menu bar's scope (#5066):
`dump_visual_tree(window: "menubar")` lists it, and `interact(target: "MenuBar/MenuItem[Game]", action: "expand",
window: "menubar")` opens it. No node there carries the code name: `NativeMenuBar` gives each node a null
`AutomationId`.

**Suggested fix.** When a Window path fails on a form whose menus are in the system menu bar, say so in the reply, and
name `window: "menubar"` and the caption path, for example `Form1's menus are in the system menu bar: use window:
"menubar", as MenuBar/MenuItem[Game]`. Possibly also carry a form menu's code name as the menubar node's
`automationId`, so a caller holding `mnuGame` from the code can reach it there. A MenuBar path already uses `[#n]` for
an index, so addressing by id there needs its own syntax.

**Fixed.** #5102 records each native item's source control for the life of its mirror. Menubar dumps and
inspection carry the source menu's code name as automationId, and a bare `#id` segment finds it at any
depth, preserving the ancestor-opening chain. A failed Window path naming one of those ids, or a Menu or
MenuItem segment, explains the system menu bar route. When that form is the bar window it gives the
caption and id paths (or discovery for a type segment); otherwise it names the current bar window.
Unrelated failures keep their existing reply. `FormMenuBarPathTests` checks the tool-level routes headlessly;
`RunningFormNamesTests` keeps the driver's unchanged failure pinned.
